# PCOSINA Production Readiness Audit

Date: 2026-03-19

> Status note (2026-03-21): this audit is now partially historical. Several findings called out below have since been mitigated in code and tests. Treat it as gap-analysis context, then confirm current status from `docs/roadmap/progress_ledger.md`, `docs/roadmap/ml_progress_ledger.md`, and `docs/release/production_readiness_checklist.md`.

## Purpose

This document records a repository-grounded production-readiness assessment of PCOSINA. The goal is not to claim that any system can be made "100 percent production ready," but to identify the concrete implementation gaps that still block an honest production-ready designation.

The assessment is based on the current codebase, release and SRE documents, workflow configuration, and deployment blueprint present in this repository.

## Executive Verdict

PCOSINA has a serious pre-production foundation, but it is not yet honest to describe the system as fully production ready.

Current classification:

- Strong thesis and prototype system
- Viable internal alpha candidate
- Plausible closed beta candidate after high-severity fixes
- Not yet defensible as public general-availability production software

The strongest positive signal is that PCOSINA already includes a real remote optimizer backend, versioned policy control, diagnostics endpoints, threat-model and runbook documents, Android and backend test suites, and machine-checkable go-live gate artifacts. The strongest negative signal is that the remaining gaps are concentrated in privileged access, mobile data protection, deployment hardening, and release governance.

## Current Strengths

- Remote optimizer authority exists on the backend, rather than only in the mobile client.
- A limited admin and operations surface already exists through:
  - `GET /admin/policy/active`
  - `GET /admin/policy/versions`
  - `GET /admin/policy/audit`
  - `POST /admin/policy/versions`
  - `POST /admin/policy/activate`
  - `POST /admin/policy/rollback`
  - `GET /ops/plan-jobs/diagnostics`
- Policy versioning, activation, rollback, and audit logging are implemented.
- The planner already supports bounded retries and controlled infeasibility handling.
- Queue and worker scaffolding exists for async planning.
- A Render deployment blueprint exists.
- Release, SRE, and threat-model documentation is already present.
- Android UI build and instrumentation coverage is materially stronger than a typical student prototype.

In short, the project is not "user-side only." It already has a backend authority layer and an initial control plane. The issue is that the control plane and operational posture are still incomplete for real production use.

## Severity Model

- P0: Must be fixed before any public production deployment
- P1: Must be fixed before a serious closed beta or pilot with external users
- P2: Important maturity work after first safe launch

## P0 Findings

### P0-1. Admin token leakage and broken production admin flow

Severity: P0

Evidence:

- `backend/main.py:167-171`
- `backend/main.py:1152-1155`
- `backend/main.py:1214-1228`
- `backend/main.py:1298-1316`

What is happening:

- The public root page constructs an admin URL containing the admin token in the query string.
- The production admin feedback page does not accept query-token authentication and instead requires `X-Admin-Token`.
- The HTML generated by the admin feedback page still embeds the token in links and hidden form inputs.
- The production delete endpoints ignore the form token and require the header instead.

Why this matters:

- Secrets must not appear in URLs or rendered HTML.
- The current flow is both unsafe and operationally inconsistent.
- In a normal production browser flow, the admin page is not properly usable.

Required implementation:

- Remove token-bearing URLs from public and admin pages.
- Remove token-bearing hidden inputs and query-string pagination links.
- Replace header-token browser usage with a real authenticated admin session or trusted operator console.

### P0-2. Admin authorization is a shared static token, not a production operator model

Severity: P0

Evidence:

- `backend/main.py:246-255`
- `backend/main.py:441-467`
- `backend/policy_store.py:75-95`

What is happening:

- All privileged configuration and diagnostic actions rely on one shared admin token.
- Audit records store an actor field, but policy mutations are recorded under the generic actor value `admin-token`.

Why this matters:

- This is not sufficient for production operator governance.
- It prevents accountability at the per-human level.
- It does not support least privilege, role separation, or revocation of one compromised operator without rotating the entire plane.

Required implementation:

- Add named operator identities.
- Add role-based access control.
- Add separate roles for content admin, policy admin, and ops admin.
- Add MFA for privileged access.
- Preserve per-operator audit attribution.

### P0-3. Admin feedback console has stored/reflected XSS risk

Severity: P0

Evidence:

- `backend/main.py:1201-1228`

What is happening:

- Feedback messages and query values are interpolated directly into HTML output.
- No escaping layer is applied before rendering those values.

Why this matters:

- Any admin-facing HTML surface that renders user-controlled content without escaping is unsafe.
- The issue affects a privileged surface, so the blast radius is higher than a normal user-facing XSS defect.

Required implementation:

- Escape all user-controlled content before inserting it into HTML.
- Prefer a templating engine with auto-escaping or a proper admin frontend.

### P0-4. Async job results are not user-scoped

Severity: P0

Evidence:

- `backend/database.py:227-257`
- `backend/main.py:1091-1096`

What is happening:

- `plan_jobs` storage does not include an owner field.
- The job fetch endpoint returns any job to any authenticated user if the job ID is supplied.

Why this matters:

- This is a cross-user data exposure risk.
- Job IDs may be hard to guess, but ownership should not rely on obscurity.

Required implementation:

- Add an owner identifier to `plan_jobs`.
- Enforce ownership checks on read and status endpoints.
- Review any other async or diagnostic result path for similar leakage.

### P0-5. Android release signing is still test-only

Severity: P0

Evidence:

- `app/build.gradle.kts:81-90`

What is happening:

- Release signing uses the default Android debug keystore.

Why this matters:

- This is not acceptable for real production release governance.
- It blocks credible release provenance and operational key management.

Required implementation:

- Replace with a real release keystore strategy or Play App Signing process.
- Store signing material outside source control and outside developer-local debug defaults.

### P0-6. Android data protection posture is not production safe

Severity: P0

Evidence:

- `app/src/main/AndroidManifest.xml:11-19`
- `app/src/main/res/xml/data_extraction_rules.xml:1-19`
- `app/src/main/res/xml/backup_rules.xml:1-13`
- `app/src/main/java/com/pcosina/app/data/repository/UserPreferencesRepository.kt:27-33`
- `app/src/main/java/com/pcosina/app/data/repository/UserPreferencesRepository.kt:90-130`

What is happening:

- `allowBackup` is enabled.
- Cleartext traffic is allowed globally.
- Backup and data extraction rules are still placeholders.
- Sensitive local artifacts such as profile, pantry, plan, grocery, and logs are persisted in DataStore-backed preferences.

Why this matters:

- The app stores health-adjacent and preference-sensitive data.
- The backup policy and storage hardening are not sufficiently defined.

Required implementation:

- Replace placeholder backup and data extraction rules with explicit include and exclude policies.
- Disable global cleartext traffic.
- Encrypt or reduce the locally stored sensitive payloads.
- Re-evaluate which data genuinely needs to remain on-device versus recoverable from the cloud.

### P0-7. Deployment blueprint is not yet a full production architecture

Severity: P0

Evidence:

- `render.yaml:1-24`
- `docs/architecture/optimizer_queue_worker.md:30-35`

What is happening:

- The repo contains a Render blueprint, but it defines only one web service and uses the free plan.
- No worker service, managed database, or managed Redis resource is declared in the blueprint.
- The async queue design assumes a worker process exists.

Why this matters:

- The project has deployment codification, but not at the level required for durable production operations.
- If the async queue path becomes active in production without a worker deployment, jobs will stall.

Required implementation:

- Declare a worker service in infrastructure.
- Declare or document required managed Postgres and Redis resources.
- Move production-only env vars and secrets into a formal deployment contract.
- Replace free-tier assumptions with capacity aligned to the target availability and latency goals.

### P0-8. Backend can silently fall back to local SQLite

Severity: P0

Evidence:

- `backend/database.py:16`
- `backend/database.py:133-147`
- `backend/policy_store.py:20-28`

What is happening:

- If `DATABASE_URL` does not point to Postgres, the backend uses local SQLite.

Why this matters:

- Silent fallback is reasonable for development.
- It is not acceptable for production infrastructure because it can hide misconfiguration and degrade durability.

Required implementation:

- Fail closed in production if required production database configuration is missing or invalid.

## P1 Findings

### P1-1. Main CI does not execute backend tests

Severity: P1

Evidence:

- `.github/workflows/ci.yml:9-179`

What is happening:

- Android builds and instrumentation tests run in CI.
- The backend job only installs dependencies.

Why this matters:

- The repository has a substantial backend test suite, but it is not enforced by the main CI merge gate.

Required implementation:

- Add a backend pytest job to main CI.
- Publish test results and coverage.
- Make backend regressions merge-blocking.

### P1-2. Production observability is only partially connected

Severity: P1

Evidence:

- `backend/main.py:59-67`
- `app/build.gradle.kts:111`
- `app/src/main/AndroidManifest.xml:29-31`
- `app/src/main/java/com/pcosina/app/PcosinaApp.kt:12-18`

What is happening:

- Backend Sentry can be enabled by environment.
- Android Sentry is effectively disabled for release builds.

Why this matters:

- Production readiness requires live crash and error visibility on both client and server sides.
- Existing repo docs also expect live alerting and canary routing evidence.

Required implementation:

- Turn on mobile release monitoring.
- Verify backend error pipelines in staging and production.
- Connect dashboards and alert routes to real destinations.

### P1-3. Rate limiting is per-process only

Severity: P1

Evidence:

- `backend/main.py:135-150`

What is happening:

- Request rate limiting is held in local memory per process.

Why this matters:

- In multi-instance deployments, this is not authoritative.

Required implementation:

- Move to a shared limiter backed by Redis or an edge platform control.

### P1-4. No production-grade mobile attestation layer was found

Severity: P1

Evidence:

- No App Check integration was found in the Android app or backend.

Why this matters:

- Production mobile services should make abuse from repackaged or scripted clients harder.

Required implementation:

- Add Firebase App Check or a similar attestation layer.

### P1-5. Network hardening is incomplete

Severity: P1

Evidence:

- `app/src/main/java/com/pcosina/app/data/repository/MealPlanRepository.kt:43-102`

What is happening:

- The HTTP client uses retries and DNS fallback, but no certificate pinning or explicit network security config hardening was found.

Why this matters:

- This leaves the release networking posture weaker than it should be for a health-adjacent app.

Required implementation:

- Add release-oriented network security config.
- Remove global cleartext.
- Decide whether certificate pinning is appropriate for the chosen backend deployment posture.

### P1-6. The admin plane is not yet a full production back-office

Severity: P1

Evidence:

- Existing admin and ops endpoints are limited to policy and diagnostics.

What is missing:

- Recipe CRUD
- Ingredient and price catalog CRUD
- Nutrition correction and review workflows
- User support and account support actions
- Plan replay or requeue tools
- Admin UI designed for authenticated operators rather than token-only access

Why this matters:

- A production service requires a content and operations plane, not only a user plane.

### P1-7. No formal database migration system was found

Severity: P1

Evidence:

- No Alembic or equivalent migration framework was found in the backend toolchain.

Why this matters:

- Ad hoc table creation is not enough for safe live schema evolution.

Required implementation:

- Add schema migration tooling and migration procedures to release engineering.

### P1-8. Firebase credential bootstrapping remains easy to misconfigure

Severity: P1

Evidence:

- `backend/main.py:201-202`

What is happening:

- The default credential path assumes `backend/secrets/firebase-service-account.json`.
- In the current workspace, the local credential file exists under a different nested path.

Why this matters:

- The secret is correctly gitignored, but the runtime path defaults are still fragile.

Required implementation:

- Standardize one production credential-loading method.
- Prefer explicit environment binding over ambiguous relative-path defaults.

## P2 Findings

### P2-1. Production proof is still incomplete even where scaffolding exists

Severity: P2

Evidence:

- `docs/roadmap/progress_ledger.md:7-14`
- `docs/release/go_live_checklist.md:3-29`
- `docs/sre/go_live_gates.md:3-35`

What the repo itself already says:

- Go-live gates are still in progress.
- Production environment provisioning is still pending.
- Production broker evidence is still pending.
- Load and chaos drills and alert routing are still not implemented.

Why this matters:

- Many of the right artifacts exist.
- What is missing is the final operational evidence that those controls are live and effective in the target environment.

### P2-2. Threat-model follow-through is incomplete

Severity: P2

Evidence:

- `docs/threat-model/production-threat-model.md:30-34`

Remaining gaps already documented by the repo:

- external secrets rotation automation
- end-to-end encryption and key-management review
- telemetry PII minimization
- formal red-team abuse-path testing

## Cross-Check Against Existing Project Documents

This audit is aligned with the repo's own stated status, not in conflict with it.

- The release checklist still contains unchecked items for gate validation, rollback readiness, alert routing, and evidence archiving.
- The SRE go-live gates still expect measurable pass evidence for safety, latency, reliability, security, and queue diagnostics.
- The roadmap ledger explicitly marks the go-live, sync hardening, optimizer hardening, and release-hardening items as in progress.

## Final Classification

PCOSINA is not "user-side only." It already includes:

- a user plane
- a remote optimizer backend
- a limited admin and operations plane

What is still missing is a production-grade privileged operator model, mobile privacy hardening, fully declared production infrastructure, and live operational evidence.

The most accurate statement is:

> PCOSINA is a strong pre-production system with meaningful hardening already implemented, but it is not yet honest to classify it as fully production ready.
